System 01 Live

Mission Control

Real-time operations dashboard

Objective
My schedule, availability, and the state of every system I run used to live in chat threads and in my head. That doesn't scale, and it doesn't survive a busy week.
Outcome
One live board: my full calendar in real time, the availability windows I set, and a health beacon for every agent on the crew — operational awareness at a glance. A desktop widget layer carries the same signals, so the state of the operation is visible without opening anything or asking anyone.
Built with
Live calendar feed · availability management · agent health beacons · desktop status widgets
System 02 Live

Agent Infrastructure

Persistent memory · session continuity · self-recovery

Objective
An agent that forgets yesterday — or stops quietly at 3 AM — is a demo, not a workforce. The crew needed real infrastructure: memory, continuity, and supervision that doesn't depend on me being awake.
Outcome
Every agent runs on persistent memory with resumable sessions, works from a task ledger with acknowledgment tracking, and is supervised by watchdogs that detect stalls, recover services autonomously, and file receipts proving what happened.
Built with
Persistent memory stores · session continuity · task ledgers · watchdog & auto-recovery services · receipt-based reporting
System 03 Doctrine

AI-Director Playbook

My methodology for directing AI agents

Objective
One prompt is not a workforce. The playbook is the system I built for giving several AI agents real jobs — and trusting the output because it gets verified, not because it sounds confident.
Outcome
Agents with defined roles, written standing orders, and checkpoints I personally clear. Work is accepted on evidence — logs, screenshots, receipts — never on an agent's say-so. Ten thousand teaching sessions taught me the core skill: explain it clearly, check the work, correct fast.
Built with
Multi-agent coordination · verification loops · human-in-the-loop checkpoints · written SOPs
System 04 In production

PeerView

Cross-agent session continuity

Objective
Long agent builds kept dying when a session stalled or hit a platform limit — the work, and everything the agent knew, stopped with it.
Outcome
A second agent reads the first agent's active and prior session state and continues the work from the exact stopping point — no lost thread, no re-briefing. Designed by me; runs across my local agent crew.
Built with
Session-state checkpoints · cross-instance state reading · local LLM + hosted agent runtimes

The Method

Direct. Build.
Verify.

Most people use AI like a search box: ask a question, get an answer, done. This is different. I run an operation — I direct, the agents build, and nothing counts as done until it has been verified. Five steps, in a loop, every working day.

01

Direct

Every engagement starts as a written brief: the outcome, the constraints, and an explicit definition of done. No vibes, no open-ended prompts — orders an agent can execute and a human can audit.

02

Build

The crew builds: a chief of staff who coordinates, specialists for systems, building, and the night watch. I design the system and set the checkpoints; the agents do the construction.

03

Verify

Work is accepted on evidence — logs, screenshots, receipts — never on an agent's say-so. If it wasn't tested, it isn't finished. This is the step most AI workflows skip, and the only one that makes the rest trustworthy.

04

Correct

Feedback is fast and specific, and every correction lands in the written standing orders — so the same mistake cannot happen twice. The rules compound even when a build doesn't.

05

Compound

Every project deposits its lessons into persistent memory the whole crew shares. The operation starts each day smarter than the last — a workforce that remembers is a workforce that improves.
